# チーム開発 個人振り返り（KPT）

対象: 2026 TechJam 夏 チーム開発プロジェクト（校内準優勝）
作成者: Karuhito
作成日: 2026-08-28

## 全体の流れ

1. 初期の要件定義・ターゲット設定は、自分（+Claude）で案を作り、メンバーには「これでOK?」程度の軽い確認しか取らずに開発に着手した
2. 中間報告（8/21）で、先生からターゲット・ペルソナ設定のズレを指摘された
3. 指摘を受け「このままではプロジェクトが失敗に終わるのではないか」という危機感から、食事・入浴・睡眠・移動時間以外のほぼ全てを開発に投入する働き方に自分を追い込んだ
4. 同時に、issueの乱立・PRの細分化という運用面の粗さも重なっていた
5. それでも友人との進捗共有や睡眠確保など最低限のセルフマネジメントは効き、校内準優勝という結果に繋がった

## Keep（継続したいこと）

- 中間報告で厳しい指摘を受け、メンタル的に厳しい状況になっても投げ出さず、残り期間でやり切り、校内準優勝まで到達した
- 精神的に厳しい状況の中でも、友人（別チームのリーダー）と進捗を共有し合う関係を保ち、睡眠時間6〜8時間は確保するなど、最低限のセルフマネジメントは機能していた

## Problem（課題）

1. **要件定義の確認が浅かった**
   要件定義の段階で、自分とClaudeで検討した案をメンバーに提示したが、「これでOK?」程度の軽い確認しか取らずに開発に着手してしまった。ターゲット・課題・解決策の論理的な整合性まで踏み込んでチームで議論できておらず、中間報告で指摘を受けた。

2. **立て直しも「機能→ターゲット」の逆順だった**
   中間報告後の立て直しも、メンバー提案の機能（スタンプ・デコる）が先にあり、それに合わせてターゲットを後付けで寄せる形になっていた。本来はターゲット→課題→解決策→機能の順であるべきだった。

3. **フロント/バックエンドの境界線を独断で設定**
   スタンプ・デコる機能の実装で、フロント/バックエンドの境界線を最初期に自分の判断で引いてしまい、結果としてhtml2canvas・Canvas 2D APIなどJS側に処理が寄りすぎた設計になった。「フロントはCSS/JS装飾まで」という境界線の中に、本来は「JS側で生成したスタンプ・落書きデータを受け取って保存するAPI」まで含めて設計すべきだったが、「装飾」という言葉に引っ張られて丸ごとフロント側の作業として切り出してしまい、バックエンドへの永続化が抜け落ちた（実際、event_page.jsを見ると、参加登録やミッション写真アップロードは `/api/events/...` にPOSTしているが、デコる機能だけそれが存在せず、Canvas 2D API → html2canvas による画像化までJS内で完結している）。

4. **issueの乱立とPRの過剰な細分化**
   issueを過剰に作成し、「1issue=1ブランチ」というルールを自分から指示。さらに自分自身もPRを細かく作りすぎた。
   - Issue: 全60件（open 7 / closed 53）
   - PR: 全73件（うち44件が自分、全体の約6割）
   - Issue/PR番号は3桁（133）まで到達
   - 自分のPRのうち7件はドキュメント更新のみで、develop への直接pushでも十分だった可能性がある

5. **メンタルのセルフマネジメント力不足**
   中間報告後（8/21〜）、「このままではプロジェクトが失敗に終わるのではないか」という危機感から食事・入浴・睡眠・移動以外のほぼ全時間を開発に投入する状態になった。この働き方が結果（準優勝）につながった実感はあるが、11日間という短期集中プロジェクトだから成立した可能性が高く、再現性のある戦略としては採用すべきでない。

## Try（次に活かすこと）

1. 最初期の案出し自体は自分（+Claude）が叩き台を作ってもよいが、その後は「これでOK?」程度の軽い確認で終わらせず、ターゲット・ペルソナ・課題・解決策の一貫性が取れているかまでチームで踏み込んで議論してから開発に着手する
2. フロント/バックエンドの境界線も、自分の判断だけで決めず、チームで議論して決める。特に「装飾」という言葉だけで判断せず、その機能が生成するデータを保存・再現する必要があるかどうかまで確認し、必要ならAPI設計をバックエンド側のタスクとして切り出す
3. issueの粒度・PRの単位を最初にチームで合意してから運用する。ドキュメント更新など軽微な変更はPRを作らず develop へ直接pushする選択肢も検討する
4. 短期決戦でどうしても踏ん張る場面は今後もあり得るが、それを「デフォルトの働き方」にはしない。次に同じような「プロジェクトが失敗に終わるのではないか」という危機感を覚える兆しが出たら、今回より早い段階（中間報告のような外部指摘を待つ前）でチームとすり合わせ、そもそも危機的状況に自分を追い込まなくて済む進め方を目指す
