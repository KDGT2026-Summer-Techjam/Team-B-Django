# 開発計画

短期チーム開発イベント（2026年8月18日 〜 8月28日）
チーム構成: 6名

---

## 確定事項（8/18）

- **フレームワーク: Django**（Flaskは使わない）
- **体制: PM 1人 / フロント 2人 / バック 3人**
- **デプロイ（Render）はリーダーが担当**

---

## スケジュール

| 日程 | フェーズ | 授業 |
| --- | --- | --- |
| 8/18（Day 1） | キックオフ・設計 | なし |
| 8/19〜8/20（Day 2-3） | MVP実装 | なし |
| 8/21（Day 4） | 中間報告 | なし |
| 8/22〜8/23 | 実装／**Must完成期限** | なし |
| 8/24〜8/26（Day 5-9） | テスト・改善 | あり |
| 8/27〜8/28（Day 10-11） | 発表・レビュー | あり |

### 方針

- **8/18〜8/23の6日間がフル稼働できる期間**。ここに寄せ切る
- **8/23をMust完成の期限とする**（8/21の中間報告は途中経過でよい）
- **8/23までに一度は全機能を繋げて動かす**（結合を後半に持ち越さない）
- 発表の骨子も8/23までに作る
- 8/24以降は、授業の合間に一人で完結できるタスク（Should）を回す
- 機能追加の提案は Should / Could に置いて処理し、**Mustは5つに保つ**

### 中間報告（8/21）

- 全員拘束はしない。リーダーが報告し、技術的な質問に答えられる人が1人同席
- **当日朝に全員で進捗を共有**（Discordへの書き込みでも可）
- **指摘された内容は当日中にチームへ共有**（反映できる時間は実質2日しかない）

## 初日（8/18）にやること

### 会議パート

1. 企画の確認（アプリ名と Should の優先順位は議論の余地を開ける／**Mustの5つは動かさない**）
2. ~~技術スタックの決定~~ → **Djangoで確定済み**
3. ポジション決め（PM 1 / フロント 2 / バック 3で確定。具体の担当割り当てを行う）
4. 稼働時間の記入（8/19〜23を特に正確に）

### 作業パート

1. リポジトリ作成、全員のclone確認
2. **デプロイ疎通**（リーダー担当。空のページでいいのでURLで開けるところまで）
3. Djangoプロジェクトの雛形を作ってpush（全員が同じ型で始められるように）
4. API仕様を確定し、`/docs/設計.md` に置いて共有
5. Figmaで画面に着手
6. Discord整備（#gneral削除、#進捗共有と#報告の用途を決める、リンク集をピン留め）
7. GitHub Issue に Must 5機能を登録し、担当者を割り当て

### 押さえどころ

- **フロント2人が手待ちになりやすい**。環境構築、ダミーデータでの画面作成、ホーム画面（API不要）を先に進めさせる
- **夕方時点で「明日から何を書けばいいか」が全員分決まっていれば成功**
- API仕様が未確定のまま終わると、8/19が丸ごと溶ける
- リーダーが最初の質問を #質問・相談 に投げておく（後続が出やすくなる）
- **`.gitignore` に `.env` が入っているか確認**

### リーダーがどこまで作るか

判断基準は作業量ではなく、**5人を止めているかどうか**。

**やる**

- リポジトリ、Djangoプロジェクトの雛形、`.env` の読み込みと配布
- Renderへデプロイして、空ページがURLで開くところまで確認
- PostgreSQL接続が通っている状態
- `models.py` に2テーブルを定義して `migrate` まで（バック3人全員がここで止まるため）
- URLルーティングの空枠を置き、担当ごとにファイルを分けておく（コンフリクト防止）
- JSONを返すダミーAPIを1本（フロントが `fetch` の形を先に確認できる）
- CSRFの扱いを決めて `/docs/` に1行で書く

**やらない**

実際のAPI 3本の中身、CSS、画面。ここに手を出すとレビューする人がいなくなり、リーダー自身がボトルネックになる。

**やめどきの判定**

夕方の時点で「**全員が `git pull` したら、自分の担当ファイルをすぐ書き始められる**」なら完了。

## チーム運営

### ポジション

| 役割 | 人数 | 備考 |
| --- | --- | --- |
| PM | 1 | リーダー。**レビュー・進行・デプロイ**。機能実装は最小限 |
| フロントエンド | 2 | 別ファイルを担当してコンフリクトを避ける |
| バックエンド | 3 | Django。下記のとおり内訳を分ける |

### バックエンド3人の内訳（推奨）

APIは3本、テーブルは2つ。**デプロイをリーダーが担当するため、3人は実装に集中できる**。

- **2人**: API実装（投稿作成・取得／参加登録）
- **1人**: モデル・マイグレーションと公開ID生成を先に作る → 終わったら**フロントへ合流**（HTML/JSなのでPythonが書ける人なら入れる）
- インフラ（Renderデプロイ、DB接続、環境変数、`.env` 配布）は**リーダー**

### 注意

- **フロント2人の負荷が一番重い**（画面5枚 + CSS）。バックの1人を早めに合流させる
- **デプロイがリーダーに集中している**。手順を `/docs/deploy.md` に残し、リーダー不在でも誰かが再デプロイできる状態にしておく
- デザイン専任を置かないため、**Figmaのモックを誰が作るか**を決める。決めないとフロント2人が見た目から考えることになる
- ホームとエラー画面はAPI不要なので、バックの人が単独で作れる。手待ち対策に使う

### 詰まった人への対応

- **2日以上進捗がない場合は、タスクの粒度を疑う**（分割するか担当を変える）
- 補助はペアで。代わりに書かない（ただし期限が迫っているなら巻き取る。その場合は明言する）
- 個人相談で受けてよいが、**解決内容は公開チャンネルに戻す**

## 完成条件（イベント要件）

- GitHubリポジトリにREADMEを作成（アプリ概要・使い方・技術スタック・担当者）
- 8/28の発表会でデモを実施。**誰の・どんな課題を・どう解決したかを3分以内で説明**

### 開発ルール

- `main` ブランチへの直接Pushは禁止
- 作業は `feature/機能名` ブランチで行い、Pull Request → レビュー → マージ
- タスクはGitHub Issueで管理（タイトルは「動詞＋対象」、担当者をAssigneesに設定）
- ラベルで Must / Should / Could を分類
- 詰まったら30分以内に相談する

### デモの構成案

1. ペルソナと課題の説明（30秒）
2. その場で誘いを作成し、QRを映す
3. **審査員や他チームに参加ボタンを押してもらう**（インストール不要なので実演可能）
4. 参加者が増える画面を見せる

**デモ用の投稿データを事前に用意しておく**（空の画面から始めない）
当日の手順は [deploy.md](deploy.md) の「発表当日のチェックリスト」を参照。
