| デプロイ | Render | **リーダー** |

### Djangoの使い方（方針）

- **DRFは使わない**。`JsonResponse` で返す
- **管理画面は使わない**。使わないなら `admin` の登録もしない
- アプリは1つでよい（イベントと参加者だけなので分けない）
- モデルはDB設計の2テーブルと対応させる。`public_id` は `unique=True`
- POSTをAPIとして受けるので、**CSRFの扱いを最初に決める**（テンプレートでトークンを渡すか、対象ビューを除外するか）。ここで詰まるパターンが多い

### デプロイ

詳細は [deploy.md](deploy.md) を参照。要点のみ:

- `SECRET_KEY` は環境変数。本番は `DEBUG = False`
- `ALLOWED_HOSTS` にRenderのドメインを入れる（入れ忘れると400）
- デプロイ時に `migrate` を走らせる
- 静的ファイルは**バックエンドから配信**する。`DEBUG = False` だとDjango単体では配信されないのでWhiteNoiseを入れる
- Renderの無料枠はスリープする。**発表デモの直前に一度アクセスして起こしておく**

## 画面ごとのUI仕様

> 配色・フォント・角丸などの共通デザインルールは [配色.md](配色.md) を参照。

### ホーム（Must）

- アプリ名・キャッチコピー（季節感を出すのはこの画面だけ）
- 「誘いを作成」ボタン（主導線。画面中央に大きく）
- 使い方の3ステップ説明（作る → 送る → 集まる）
- **★Should** 参加予定イベント一覧への導線（visitor_idの参加履歴があるときだけ表示）
- **★Could** 季節エフェクト（下記）

#### 季節エフェクト（★Could ─ Must外。余裕が出たら着手）

ホームの背景に、その時期の季節に合わせた粒を降らせる。**「季節に特化したアプリ」というコンセプトを、文章で説明せずに見せられる唯一の画面**。

| 時期 | エフェクト |
| --- | --- |
| 3〜5月 | 桜の花びら（揺れながら落ちる） |
| 6〜8月 | **花火**（上がって開く。他の3つと違い上向き） |
| 9〜11月 | 落ち葉（回転しながら落ちる） |
| 12〜2月 | 雪（まっすぐに近い形で落ちる） |

判定は**アクセスした日の月**で行う（イベントの開催日ではない）。`new Date().getMonth()` で分岐するだけ。

**実装の約束**

- **CSSアニメーションで作る**。Canvas と requestAnimationFrame は使わない（凝り出すと止まらないため）
- 粒は**30個程度**。JSで生成して、位置・遅延・速度をランダムに振る
- 目安90行以内。超えそうなら止める
- ボタンを遮らないこと。`pointer-events: none` を忘れない
- `prefers-reduced-motion` が有効な端末では動かさない
- **ホームのみ**。投稿ページには入れない（初めて来た人の参加ボタンを邪魔する）

**発表デモへの注意**

- **発表は8/28なので、審査員に見えるのは花火だけ**。まず花火を作り、残り3つは後回しでよい
- 4つ全部見せたいなら、`?season=spring` のようなクエリで強制切り替えできるようにしておく

### 投稿作成（Must）

- 入力項目: イベント名、開催日（dateピッカー）、場所、投稿者名
- 全項目必須。未入力のときは送信ボタンを無効にする
- 開催日は**過去日を選べなくする**（残り日数がマイナスになるのを防ぐ）
- エラーは項目の直下に赤字で出す

### 投稿完了（Must）

- 生成された共有文を**編集可能なテキストエリア**で表示（末尾に共有URLを含む）
- 「コピー」ボタン。押したら「コピーしました」とフィードバックを出す
- 自分の投稿ページを開くリンク
- **★Should** 編集トークン付きURLの受け渡し。渡せるのはこの画面だけなので、失うと編集できなくなる旨を明記する（編集機能を作らないうちはこの表示も不要）

### エラー画面（Must）

- 「この誘いは見つかりませんでした」と、URLが間違っているか削除された可能性の説明
- ホームへ戻るボタン

### 参加予定イベント一覧（★Should ─ Must外）

自分が参加したイベントをまとめて見る画面。**これがなくてもMVPの一本道（作る→送る→開く→参加）は成立する**ため、Mustには入れない。

```
┌────────────────────────┐
│  参加予定のイベント       │
│                          │
│  あと2週間                │
│  長岡花火大会           │  ← タップで投稿ページへ
│  8/22（金）・長岡市        │
│  ────────────────────  │
│  あと42日               │
│  ぶどう狩り               │
│  10/1（水）・南魚沼市      │
│                          │
│  ── 終わったイベント ──   │  ← 過去分は下にまとめる
│  桜見（4/5）              │
└────────────────────────┘
```

- 開催日の**近い順**に並べる。各行はイベント名・開催日・残り日数・場所
- 行をタップしたらその投稿ページへ（参加後の状態で開く）
- 過去のイベントは下に分けて置く。削除はしない
- 履歴が0件のときは、**ホームの導線ごと出さない**（空の画面を見せない）

**実装するときの注意**

- **公開IDの配列ではなく、visitor_idから引く**。`Participant.visitor_id` が自分のvisitor_idと一致する行から参加イベントを、`Event.creator_visitor_id` が一致するイベントから自分が作成したイベントを、それぞれサーバー側で集計する
- イベント名や日付はフロントに保存せず、表示のたびにAPIから取り直す（投稿が編集されたとき古い情報が残るため）
- **新しいAPIが1本必要になる**。`request.visitor_id` を見て、参加中／作成済みのイベント一覧をまとめて返すエンドポイントを追加する。**MustのAPI 3本には含まれていない**ので、着手前にバックと決める
- **端末をまたげない**。別の端末で開くと空になる（Cookieが無いため）。デモで見せるなら自分の端末で

## 投稿ページの2状態

> **投稿ページは画面が2枚あるのではなく、1枚の画面が2つの状態を持つ。**
> URLは同じ。遷移もしない。参加ボタンを押すと同じページの中身が差し替わる。

### 状態A: 参加前

```
┌────────────────────────┐
│  あと2週間                │  ← ★Should（なくても成立）
│  長岡花火大会           │
│  8月22日（金）           │
│  新潟県長岡市             │
│  田中 が誘っています     │
│                          │
│  今の参加者（2人）        │  ← 自分は入っていない
│  ・佐藤  ・鈴木            │
│                          │
│  名前：[            ]    │  ← 参加前にだけある
│  【  参加する  】          │
└────────────────────────┘
```

### 状態B: 参加後

```
┌────────────────────────┐
│  あと2週間                │
│  長岡花火大会           │  ← 上半分は完全に同じ
│  8月22日（金）           │
│  新潟県長岡市             │
│  田中 が誘っています     │
│                          │
│  参加しました              │  ← 完了の合図
│                          │
│  参加者（3人）           │
│  ・佐藤  ・鈴木  ・あなた  │  ← 自分が加わっている
│                          │
│  参加を取り消す            │  ← ★Should。ボタンではなく小さいリンク
└────────────────────────┘
```

### 差分一覧

| 要素 | 参加前 | 参加後 |
| --- | --- | --- |
| イベント情報（名前・日付・場所・主催者） | 表示 | 表示（同じ） |
| 残り日数 **★Should** | 表示 | 表示（同じ） |
| 参加者一覧 | 表示（自分は含まない） | 表示（自分を含む） |
| 名前入力欄 | あり | **なし** |
| 参加ボタン | あり | **なし** |
| 「参加しました」表示 | なし | **あり** |
| 参加を取り消すリンク **★Should** | なし | **あり** |

> **Mustの範囲だけで作る場合**は、残り日数と取り消しリンクを外して、
> 【イベント情報 + 参加者一覧 + 名前入力 + 参加ボタン】の4要素だけになる。それでもMVPの一本道は通る。
> ただし**残り日数はShouldの最優先**（このアプリの独自性そのもの）なので、Mustが終わったら真っ先に入れる。
> レイアウトを決める段階で**場所を空けておく**と後で楽。

### 状態の判定方法

- `GET /api/events/:public_id` は**どちらの状態でも同じJSONを返す**（イベント情報 + 参加者配列）。このAPI自体は「見ている人が誰か」を知らない
- **参加済みかどうかは投稿ページのHTMLを返す時点でサーバーが判定する**。`Participant.visitor_id` に自分の `visitor_id`（Cookie）があるかをサーバー側で調べ、`is_participant` として投稿ページのテンプレートに渡す（`body`要素の `data-is-participant` 属性に埋め込む）
- フロントは初期表示時にこの `data-is-participant` を読み、参加前／参加後どちらの見た目で組み立てるかを決める
- 参加ボタンを押したら: POST → レスポンスの参加者一覧を使って**ページを再読み込みせずにDOMを書き換える**
- 別の端末やプライベートブラウジングで開くと参加前に戻る（`visitor_id` Cookieが無いため新しく発行される）。**これは仕様**（アカウントなしの割り切り）
- 二重参加は厳密には防げない。同名が並んだら作成者が気づけるので、Mustの範囲では対策しない

## 遷移図

```
[ホーム]
   ↓ 「誘いを作成」
[投稿作成]
   ↓ 送信
[投稿完了]  ── 共有文をコピーしてLINEへ ──┐
   ↓ 自分の投稿を確認                      │
[投稿ページ] ←──────────────────────────────┘
   ↓ 参加ボタン                    （リンクを受け取った人）
[投稿ページ・参加後]

[エラー画面] ← 存在しない公開IDでアクセスされたとき
```

### 補足

- **投稿ページは同一URLで2状態を持つ**（参加前／参加後）。画面遷移ではなく**状態遷移**として描く
- **投稿ページに来る人はアプリを初めて見る人**。友達からLINEでリンクを受け取って開くため、「これは何のページか」が分からないと参加ボタンを押してもらえない。**最も丁寧に設計する画面**
- 投稿完了画面から投稿ページへのリンクを置く（作成者が自分の投稿を確認できる）
- 参加ボタンを押した後は同じページに留まり、参加者一覧を表示する（完了画面を挟むより実装が楽）
- **ホームはAPI不要**なので、設計待ちの間にフロントが着手できる
- ホームは**季節感を出せる唯一の画面**。他は機能に徹する

## visitor_idの仕組み（追加設計）

アカウントが無いため、サーバーは「見ている人が誰か」を単体では知らない。しかし「誰が作成したか」「誰が参加済みか」はサーバー側でも判定できる必要がある（投稿ページの参加前／参加後の判定、編集画面の認可判定、参加予定イベント一覧のサーバー側集計など）。この課題に対応するため、Cookieベースの `visitor_id` を導入し、状態判定はこれを唯一の手段とする（localStorageは使わない）。

- **発行方法**: `events/middleware.py` の `VisitorIdMiddleware` が、リクエストに `visitor_id` Cookieが無ければ発行する
  - Cookie名: `visitor_id`
  - 値: `secrets.token_urlsafe(16)`（`edit_token`と同じ生成方式）
  - 属性: `httponly`, `SameSite=Lax`, 有効期限1年
  - 各viewからは `request.visitor_id` で参照する
- **用途**:
  - `Event.creator_visitor_id`: イベント作成時のvisitor_idを保存し、作成者本人かどうかの判定に使う（my card一覧の抽出、編集画面の認可の一つ）
  - `Participant.visitor_id`: 参加登録時のvisitor_idを保存し、参加済みかどうかの判定に使う（`is_participant`のサーバー側判定、参加予定イベント一覧の抽出）
- **localStorageは使わない**: 状態判定はvisitor_id（Cookie）のみで行う。同じブラウザなら、別タブ・別ウィンドウはもちろん、一度閉じて後日開き直しても（＝ブラウザのセッションをまたいでも）同じCookieが有効な限り保持される。一方、**別のブラウザアプリ・別端末・プライベートブラウジング**は別のCookie保管領域になるため、参加前の状態に戻る（これは仕様）
- **編集画面の認可**: 編集トークン（URLのクエリパラメータ）または `creator_visitor_id` の一致、いずれかで許可する
- **ミッション写真アップロードの認可**: 編集トークンは使わず、`participants.visitor_id` に自分の `visitor_id` があるか（参加者）、または `creator_visitor_id` と一致するか（作成者）のいずれかで許可する。`visitor_id` が空のリクエストは無条件で拒否する（詳細はDB設計の `missions`、API設計を参照）

## API設計

| メソッド | パス | 用途 | 区分 |
| --- | --- | --- | --- |
| POST | `/api/events` | 投稿作成 | Must |
| GET | `/api/events/:public_id` | イベント情報 + 参加者一覧（+ ミッション一覧は★Should） | Must |
| POST | `/api/events/:public_id/participants` | 参加登録 | Must |
| PATCH | `/api/events/:public_id` | 投稿の編集（トークン必須） | ★Should |
| DELETE | `/api/events/:public_id/participants/:id` | 参加の取り消し | ★Should |
| GET | `/api/events?ids=a7k2m9,b3n8p2` | 一覧画面用のまとめ取得 | ★Should |
| POST | `/api/events/:public_id/missions/:mission_id/photo` | ミッション写真の登録（参加者・作成者） | ★Should |

> **MustはAPI 3本**。これだけでMVPの一本道（作る→送る→開く→参加）は通る。
> 下の3本はShouldで、**8/23の期限には含まない**。

### POST /api/events（投稿作成）

```json
// リクエスト
{
  "title": "長岡花火大会",
  "event_date": "2026-08-22",
  "location": "新潟県長岡市",
  "organizer_name": "田中"
}

// レスポンス 201
{
  "public_id": "a7k2m9",
  "edit_token": "xY3kP...",
  "url": "https://xxx.onrender.com/e/a7k2m9"
}
```

- **`edit_token` を返すのはこのレスポンスだけ**。GETでは絶対に含めない（含めると誰でも編集できてしまう）
- 共有文の生成は**フロント側**で行う（サーバーはURLを返すだけ）

### GET /api/events/:public_id（取得）

```json
// レスポンス 200
{
  "public_id": "a7k2m9",
  "title": "長岡花火大会",
  "event_date": "2026-08-22",
  "location": "新潟県長岡市",
  "organizer_name": "田中",
  "participants": [
    { "id": 1, "name": "佐藤" },
    { "id": 2, "name": "鈴木" }
  ],
  "missions": [
    {
      "id": 12,
      "order": 1,
      "prompt_text": "全員で1枚撮る",
      "photo": "data:image/png;base64,iVBORw0KGgo...",
      "completed_at": "2026-08-21T10:00:00+09:00"
    },
    {
      "id": 13,
      "order": 2,
      "prompt_text": "ごはんを撮る",
      "photo": null,
      "completed_at": null
    }
  ]
}
```

- **参加前でも参加後でもこの形を返す**。サーバーは見ている人が誰かを知らない
- 参加者が0人のときは `[]` を返す。`null` にしない（フロントで分岐が増えるため）
- `missions` **★Should**（スタンプラリー機能）。`order` の昇順で返す。ミッションが未登録のイベントでは `[]` を返す
- `photo` が `null` の要素は未クリア。進捗（「1/3クリア」）は**フロント側で数える**（残り日数と同じ方針）
- **`photo` はBase64文字列なので1件あたりのレスポンスが重くなる**。写真が増えて遅い場合は、一覧用に `photo` を含めない形へ分ける（着手前にバックと相談）

### POST /api/events/:public_id/participants（参加）

```json
// リクエスト
{ "name": "山田" }

// レスポンス 201
{
  "id": 3,
  "name": "山田",
  "participants": [
    { "id": 1, "name": "佐藤" },
    { "id": 2, "name": "鈴木" },
    { "id": 3, "name": "山田" }
  ]
}
```

- **更新後の参加者一覧をまるごと返す**。フロントはこれをそのまま描画すればよく、GETをもう一度叩かなくて済む
- 返ってきた `id` は、取り消し（★Should）で使う

### POST /api/events/:public_id/missions/:mission_id/photo（ミッション写真の登録 ★Should）

撮った本人がその場で上げられるように、**作成者だけでなく参加者も実行できる**。

```json
// リクエスト
{ "photo": "data:image/png;base64,iVBORw0KGgo..." }

// レスポンス 200
{
  "id": 12,
  "order": 1,
  "prompt_text": "全員で1枚撮る",
  "photo": "data:image/png;base64,iVBORw0KGgo...",
  "completed_at": "2026-08-21T10:00:00+09:00"
}
```

- **そのイベントの参加者、または作成者だけが実行できる**。`participants` に自分の `visitor_id` があるか、`creator_visitor_id` と一致するかをサーバー側で確認し、どちらでもなければ403
- **`edit_token` はここでは使わない**（参加者は持っていないため）。編集（`PATCH /api/events/:public_id`）とは判定が違う点に注意。作成者が別ブラウザから上げたい場合は、参加ボタンを押して参加者になれば通る
- `photo` はBase64文字列。DBの `missions.photo` にそのまま保存する（ファイルとして保存しない。理由はDB設計の `missions` を参照）
- 登録に成功した時点で `completed_at` が入り、そのミッションはクリア扱いになる
- 写真の差し替えも同じエンドポイントで行う（**後から上げた写真で上書きされる**）。**取り消し（クリア解除）はShouldの範囲外**

### 値の約束

- **日付は `YYYY-MM-DD` の文字列で返す**。「8月22日（金）」のような整形はフロント側
- **残り日数はサーバーで計算しない**。日付を渡してフロントで引く（キャッシュで古い日数が残るのを避ける）
- `public_id` は6文字。`participants` と `missions` は常に配列
- キー名は**DBのカラム名と揃える**（変換を挿まない）

### エラーの返し方

| コード | いつ |
| --- | --- |
| 400 | 必須項目がない、日付が不正、名前が空、写真データが空 |
| 403 | 編集トークンが不一致（＝作成者でない）、ミッション写真をそのイベントの参加者でも作成者でもない人が登録しようとした |
| 404 | その `public_id` のイベントがない、その `mission_id` のミッションがない |

```json
{ "error": "イベントが見つかりません" }
```

- エラーの形は**この1種類だけ**に統一する。細かく分けない

### 着手前に決めること

- **CSRFの扱い（8/18確定）**: `csrf_exempt` は使わない。テンプレートに `{% csrf_token %}` を置き、JSは `document.cookie` の `csrftoken` を読むか、hidden inputの値を `X-CSRFToken` ヘッダに付けて `fetch` する
- フロントはこのJSON例をダミーとして先に画面を作れる。**APIの完成を待たない**

### missions ★Should（スタンプラリー機能）

| カラム | 型 | 備考 |
| --- | --- | --- |
| id | serial | |
| event_id | int | `events.id` への外部キー |
| order | int | 表示順（1, 2, 3…） |
| prompt_text | varchar | ミッション文言（例:「全員で1枚撮る」） |
| photo | text | アップロードされた写真（**Base64文字列**）。**nullなら未クリア** |
| completed_at | timestamp | 写真がアップロードされた日時。nullなら未クリア |

- **1ミッション = 1枚の写真枠**。写真のアップロード＝そのミッションのクリアで、**参加者なら誰でも行える**（作成者に限定しない）。撮った本人がその場で上げられるようにするため。作成者だけに限ると、参加者が撮った写真をLINE等で作成者に送り、作成者がダウンロードして上げ直す手間が毎回発生する
- **写真はファイルではなくBase64文字列としてDBに保存する**（`TextField`）。Renderの無料プランはディスクが永続化されず、`ImageField`でローカル保存するとスリープ復帰・再デプロイのたびに写真が消えるため。`Pillow`・`MEDIA_ROOT`の設定は不要
- クリア判定の正は `photo`。`completed_at` は「いつクリアしたか」を記録する補助的なカラムで、判定条件には使わない
- 進捗（「0/3クリア」）は**カラムに持たず、その都度数える**。`events` 側にカウント用カラムは追加しない（編集で増減したとき古い値が残るため）。数えるのはフロント側＝GETで返る `missions` のうち `photo` が入っている件数（残り日数と同じ方針）
- 認可は新しいカラムを追加せず、既存の `participants.visitor_id`（参加登録済みか）と `events.creator_visitor_id`（作成者か）で判定する。どちらにも当てはまらなければ403。**作成者は `participants` に入っていないことがある**ので、必ず「参加者 **or** 作成者」の2条件で見る
- **`visitor_id` が空のリクエストは無条件で拒否する**。`participants.visitor_id` はnull許容なので、空のまま絞り込むとnullの参加者に一致して誰でも通ってしまう
- 同じミッションに後から別の写真を上げると**上書きされる**（1ミッション1枚固定のため）。誰が上げたかは記録しない。取り違えても上げ直せることを優先し、先着固定にはしない
- `mission_photos` のような別テーブルには分けない（1ミッション1枚固定のため）

- 内部IDと `public_id` を分けるのは、外部キーの参照を数値で持てるため。URLには `public_id` だけを出す
- **usersテーブルは今は作らない**。アカウント機能はShould最下位であり、今作るとMust部分の設計が重くなる

## ID生成のルール

- **`secrets` モジュールを使う**（`random` は擬似乱数なのでIDには使わない）
- 紛らわしい文字（`0/O`、`1/l/I`）を候補から除外する
- 生成後にDBの重複チェック。カラムにUNIQUE制約を付ける
- 公開IDは短く（共有するもの）、編集トークンは長く（共有しないもの）

```python
import secrets

chars = 'abcdefghjkmnpqrstuvwxyz23456789'
public_id = ''.join(secrets.choice(chars) for _ in range(6))
```

## 認可の方針

- **認可チェックは必ずサーバー側で行う**
- 編集トークンをDBと照合し、不一致なら403
- **ミッション写真のアップロードは編集トークンを使わない**（参加者はトークンを持っていないため）。`visitor_id` が参加者一覧または作成者と一致するかで判定する（詳細は「visitor_idの仕組み」を参照）
- クライアント側の状態（フォーム入力値など）を認可判断に使わない。改ざん可能なため、判断は必ずサーバー側の `visitor_id`・`edit_token` で行う（詳細は「visitor_idの仕組み」を参照）
- **Mustの範囲ではアカウント認証を実装しない**。参加者名は自由入力
