# 要件定義

最終更新: 2026年8月18日

---

## テーマ

季節のイベント・レジャー・グルメ・自然・癒しをより快適にするサービス

---

## ターゲット

高校時代の友人など、**進学先が分かれて日常的に会わなくなった友達**と、季節のイベント（花火大会・紅葉・味覚狩りなど）に行きたいと思っている大学1〜3年生。

行きたい気持ちはあるが、相手の予定や興味を把握しておらず、久しぶりに個別で連絡を取るのは気が引けると感じている。

---

## 課題

- 学校や進学先が別々で、**日常的に会う機会がない**
- そのため、誰がそのイベントに興味を持っているか**分からない**
- 相手の予定が空いているかも、**聞いてみないと分からない**
- 久しぶりの連絡は切り出しにくく、**最初の一言が書けない**
- グループチャットに流しても、**反応がないまま流れて終わる**

結果として、**行きたかったのに行かないまま季節が終わる**。

---

## 解決策

**イベントの誘いを共有URLつきで作成し、受け取った人が参加ボタンを押すだけで意思表示できるようにすることで、個別に誘わずに同行者を集められる。**

---

## MVP

これが動けば課題を解決したと言える最小の流れ。

```
Aが誘いを作る
  → 共有文をコピーしてLINEに貼る
    → Bがリンクを開く
      → 参加ボタンを押す
        → Aに参加者が見える
```

**この一本が通ればMVP成立。**
機能追加の提案が出たら「その機能がなくてもこの流れは成立するか」で判断し、成立するなら Should 以下に置く。

---

## 機能一覧

### Must（必須）

1. 誘いの投稿作成（イベント名・日付・場所・投稿者）
2. 投稿ごとの共有URL発行
3. 投稿ページの表示
4. 参加ボタンと参加者の表示
5. 共有文の生成（テンプレート）とコピー機能

> **Mustは5つに保つ。増やさない。**

### Should（重要）

| 優先 | 機能 | 備考 |
| --- | --- | --- |
| 1 | 開催日・見頃までの残り日数表示 | **このアプリの独自性そのもの。最優先** |
| 2 | 成立ライン設定（「2人以上で決行」） | |
| 3 | 参加が入ったときの通知 | |
| 4 | 投稿の編集機能 | 編集トークンによる認可 |
| 5 | 参加予定イベント一覧 | localStorageに参加履歴を保存 |
| 6 | アカウント機能 | **Should内で最下位。上の5つが終わってから着手** |

> アカウント機能を入れる場合も、**参加ボタンにログインを要求しない**。投稿者が自分の投稿を管理するための機能であり、参加者側の体験（リンクを開くだけ）は変えない。

### Could（余裕）

- AIによる誘い文の生成（トーン選択つき）
- 天気情報の表示
- グループ機能（同じメンバーで繰り返し使う）
- イベント種別の自由入力（日常の予定にも対応）
- 過去に参加したイベントの記録
- 近隣スポット
- 季節エフェクト（ホーム画面。春=桜／夏=花火／秋=落ち葉／冬=雪）
  アクセスした日の季節で切り替える。コンセプトを説明なしに見せられるが、MVPの一本道には登場しない

---

## 設計方針

- **インストール不要・アカウント登録不要のWebアプリ**とし、リンクを開くだけで使える形にする
- グループ作成を前提にせず、**投稿ごとに共有URLを発行**する（初回利用の障壁を下げるため）
- 生成文は**送信しない**。コピーして自分で手直しし、LINE等に貼る流れに留める
- 生成文は編集可能なテキストエリアで表示し、コピーボタンを付ける
- 生成文の末尾に共有URLを自動で含める

---

## 想定される質問への回答

### 「直接言えばいいのでは？」

学校が違って会う機会がないため、**そもそも言う場面が存在しない**。加えて、久しぶりの連絡は切り出す負担が大きい。その負担を共有URLと文面生成で肩代わりする。

心理（奥手・言い出しにくい）ではなく、**情報の欠落と物理的な制約**として説明する。

### 「既存サービスと何が違うのか？」

- **ウェザーニュース（花火の天気）** … 開催地と天気で完結しており、「誰と行くか」を一切扱っていない
- **LINE** … 汎用チャットのため、季節イベントの期限（開催日・見頃）を扱わない

この**両者の隙間**にある領域を狙っている。

### 「対象が狭いのでは？」

狭いのは対象ではなく、解いている**場面**。「行きたいと思ってから声をかけるまで」の一点に絞っている。対象自体は広い。

### 「日常の予定調整にも使えるのでは？」

使える。ただし説明は**季節イベント特化**で通す。汎用性を前に出すとテーマから外れ、LINEとの比較で不利になるため。拡張性は発表の「今後の展望」で触れる。

### 「継続的に使われるのか？」

頻度は低い。ただし**季節は毎年必ず巡る**ため、需要が消えることはない。

### 「アカウント機能はいらないのか？」

- MVPの流れ（作る→送る→開く→参加する）に登場しない
- 「気軽に誘えない」という課題と逆行する。参加側の手数が増える
- 認証で解けることは他の手段で解ける（一覧→localStorage、編集権限→編集トークン）
- 工数がMust級。8/23の完成期限を圧迫する
- **デモで審査員にその場で参加ボタンを押してもらえなくなる**（登録が必要になるため）
