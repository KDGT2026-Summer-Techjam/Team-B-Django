# 要件定義

最終更新: 2026年8月25日

---

## テーマ

季節のイベント・レジャー・グルメ・自然・癒しをより快適にするサービス

---

## ターゲット

季節のイベントや遊びに、仲の良い友人グループと実際に行きたいと思っている中高生。
誘いたい気持ちはあるのに、日程調整や人数把握の手間で腰が重くなり、誘うタイミングを逃してしまう。

---

## 課題

- 参加者を募ったけど、**日程の調整がなかなかまとまらない。**
- 参加者を招待したけど、**アカウントの作成や煩わしいログイン**があって面倒。
- 誘った後、実際に誰が来るのか**個別に確認して回るのが手間**で、結局人数がはっきりしないまま当日を迎える

結果として、**行きたかったのに行かないまま季節が終わる**。

---

## 解決策

**イベントの誘いを作成しURLを共有、受け取った人が名前を入れて参加ボタンを押すだけで意思表示できるようにすることで、誘った後の参加確認・人数把握の手間をなくせる。**

---

## MVP

これが動けば課題を解決したと言える最小の流れ。

```
Aが誘いを作る
  → 共有文をコピーしてLINEに貼る
    → Bがリンクを開く
      → 参加ボタンを押す
        → Aに参加者が見える
```

**この一本が通ればMVP成立。**
機能追加の提案が出たら「その機能がなくてもこの流れは成立するか」で判断し、成立するなら Should 以下に置く。

---

## 機能一覧

### Must（必須）

1. 誘いの投稿作成（イベント名・日付・場所・投稿者）
2. 投稿ごとの共有URL発行
3. 投稿ページの表示
4. 参加ボタンと参加者の表示
5. 共有文の生成（テンプレート）とコピー機能

> **Mustは5つに保つ。増やさない。**

### Should（重要）

| 優先 | 機能 | 備考 |
| --- | --- | --- |
| 1 | 開催日・見頃までの残り日数表示 | **このアプリの独自性そのもの。最優先** |
| 2 | スタンプラリー（季節イベント当日の写真ミッション・順次アンロック・画像保存/共有） | **LINE・生成AI・Googleフォームとの差別化の核。issue #73・#85で実装中** |
| 3 | 成立ライン設定（「2人以上で決行」） | |
| 4 | 参加が入ったときの通知 | |
| 5 | 投稿の編集機能 | 編集トークンによる認可 |
| 6 | 参加予定イベント一覧 | localStorageに参加履歴を保存 |
| 7 | アカウント機能 | **Should内で最下位。上の6つが終わってから着手** |

> アカウント機能を入れる場合も、**参加ボタンにログインを要求しない**。投稿者が自分の投稿を管理するための機能であり、参加者側の体験（リンクを開くだけ）は変えない。

### Could（余裕）

- AIによる誘い文の生成（トーン選択つき）
- 天気情報の表示
- グループ機能（同じメンバーで繰り返し使う）
- イベント種別の自由入力（日常の予定にも対応）
- 過去に参加したイベントの記録
- 近隣スポット
- 季節エフェクト（ホーム画面。春=桜／夏=花火／秋=落ち葉／冬=雪）
  アクセスした日の季節で切り替える。コンセプトを説明なしに見せられるが、MVPの一本道には登場しない

---

## 設計方針

- **インストール不要・アカウント登録不要のWebアプリ**とし、リンクを開くだけで使える形にする
- グループ作成を前提にせず、**投稿ごとに共有URLを発行**する（初回利用の障壁を下げるため）
- 生成文は**送信しない**。コピーして自分で手直しし、LINE等に貼る流れに留める
- 生成文は編集可能なテキストエリアで表示し、コピーボタンを付ける
- 生成文の末尾に共有URLを自動で含める

## 想定される質問への回答

### 「直接言えばいいのでは？」

直接誘うこと自体は自然にできるし、それで構わない。ただし、「行こう」と声をかけただけでは**誰が実際に来るのか正式に把握できず**、人数把握や日程の再確認を個別にやり取りする手間が残る。その部分（参加の意思表示・人数の可視化・当日の記録）を共有URLが肩代わりする。

「言うか言わないか」ではなく、**「言った後に何が残るか」**として説明する。

### 「既存サービスと何が違うのか？」

- **ウェザーニュース（花火の天気）** … 開催地と天気で完結しており、「誰と行くか」を一切扱っていない

#### 発表本番で使う3つの比較（中間報告で実際に受けた指摘への回答）

- **LINE** … 招待を送る手段としてはLINEに乗っかる前提でよい。ただしLINE自体は季節イベントの期限（開催日・見頃）を扱わず、当日の記録を1つの成果物として残す仕組みも持たない。**送る手段はLINEでも、送った先でこのアプリを使う理由（期限管理＋スタンプラリーの記録）がある**
- **Geminiなどの生成AIに直接頼めばいいのでは？** … 誘い文の生成はできても、**季節イベント当日にしか作れない**「その場にいたグループ全員で埋めていくスタンプカード」という、**二度と作れない一点物**の成果物までは生成できない
- **Googleフォームで参加可否だけ取ればいいのでは？** … 可否は取れても、「行った後に残るもの」が無い。スタンプラリーは、**その季節・その1回だけの**一点物として参加後に手元に残る思い出を作る点でフォームと役割が異なる

#### その他の比較（発表では省くが、裏取り済みの回答）

- **調整さん・LINEスケジュールなどの日程調整ツール** … **ここは正直に役割が違うと認める。** 複数候補日から最適な1日を見つける精度では、これらの専用ツールに勝てない。このアプリは「日付がある程度決まった後」の招待・参加確認・当日の記録を担当する立ち位置であり、日程調整そのものを置き換えるとは主張しない
- **GooseChase・PicCollage・Instagramのステッカー機能などの写真ミッション／装飾系ツール** … 個別の機能（写真ミッション、装飾）だけを見ればどれかに代替されうる。ただし、①アカウント登録・導入コストなしで、②3〜5人の一回限りのカジュアルな集まりのためだけに、③その日専用の1枚の成果物として残せる、という3条件を同時に満たすツールは無い

**調整さんのような日程調整の専門ツールとは役割を分け**、それ以外のサービスとの**隙間**にある領域を狙っている。

### 「対象が狭いのでは？」

狭いのは対象ではなく、解いている**場面**。「声をかけてから、参加者が確定・記録されるまで」の一点に絞っている。対象自体は広い。

### 「日常の予定調整にも使えるのでは？」

使える。ただし説明は**季節イベント特化**で通す。汎用性を前に出すとテーマから外れ、LINEとの比較で不利になるため。拡張性は発表の「今後の展望」で触れる。

### 「中高生以外にも使えるのでは？」

使える。友人グループで日程調整・参加確認・当日の記録をしたいという構造は年齢を問わない。ただしピッチでは**中高生の季節イベント**という具体的な場面に絞って説明する。対象を「学生」まで広げると生活スタイルの幅が大きすぎて説得力が薄まるため。大学生などへの拡張は「今後の展望」で触れる。

### 「継続的に使われるのか？」

頻度は低い。ただし**季節は毎年必ず巡る**ため、需要が消えることはない。

### 「アカウント機能はいらないのか？」

- MVPの流れ（作る→送る→開く→参加する）に登場しない
- 参加側の手数が増える。**「名前を入れて参加ボタンを押すだけ」まで参加ハードルを最小限に抑えた設計判断そのものを崩す**
- 認証で解けることは他の手段で解ける（一覧→localStorage、編集権限→編集トークン）
- 工数がMust級。**8/23のMust機能完成期限**（発表日8/28とは別）を圧迫する
- **デモで審査員にその場で参加ボタンを押してもらえなくなる**（登録が必要になるため）
